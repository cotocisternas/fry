# Send outgoing email through an existing SMTP relay

The first release of FRY will accept outgoing email from business applications and hand it to an existing SMTP relay, keeping Internet delivery with that relay. This includes outbound routing in FRY without making direct delivery to recipient mail servers part of the initial scope; submission details, retry scheduling and limits, and delivery-status reporting remain open.

The first milestone supports a shared default SMTP relay per FRY installation and an optional organization-specific override with its own last-mile MTA server and credentials. Organizations without an override use the shared default; an opted-out organization selects its own downstream MTA. This does not add direct-to-recipient Internet delivery by FRY. Configuration permissions, validation, changes affecting queued messages, and any failover between relay destinations remain open; automatic fallback from an organization-specific MTA to the shared relay has not been authorized.

FRY durably accepts and queues outgoing submissions even when the selected downstream relay/MTA is unavailable, then retries that destination. After acceptance, FRY owns pending handoff and retry progress; this requires recoverable message bytes and queue state under the active deployment profile and its agreed degraded-operation policy. Acceptance by FRY, acceptance by the downstream MTA, and final recipient delivery are distinct outcomes. Outbound retries have a configurable bounded period. If FRY still cannot hand the message to the selected MTA when that period ends, it stops retrying, sends a delivery-failure notice to the submitting sender, and records the failure for administrators. This is a terminal handoff failure, not a declaration that downstream delivery succeeded or that the original bytes are immediately deleted. The user explicitly leaves the default retry duration undecided; no hours/days value is selected. Duration selection and configuration scope, retry-clock start, queue admission/capacity limits, retry backoff, handling permanent rejection before the deadline, failure-notice addressing/delivery, post-failure recovery retention, and ambiguous downstream acknowledgments remain open.

FRY restricts outgoing sender identities to domains or addresses explicitly authorized for the submitting organization, including approved send-on-behalf-of addresses. Authentication alone does not permit arbitrary sender identities. Assigned organization managers and global operators may grant these authorizations, including send-on-behalf-of identities; managers remain limited to their assigned organizations. Before enabling a new outgoing sender domain or address, FRY must verify control or delegation. A global operator may override this requirement with a recorded override; organization managers cannot bypass verification. Verification mechanisms, evidence lifecycle and revocation, override audit details, which envelope/header fields are checked, and treatment of forwarding and null reverse-path messages remain open.

The user confirms that existing downstream relay/last-mile MTAs support authenticated SMTP on ports 587 or 465. This allows the reported outbound connections to avoid AWS's default public-port-25 restriction if AWS is selected; provider/account connectivity and future relay capabilities still require validation.
