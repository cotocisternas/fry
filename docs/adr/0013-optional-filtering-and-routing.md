# Make filtering and application routing optional

FRY must operate as conventional email infrastructure for existing integrations without requiring filtering, attachment classification, routing rules, or fallback-application configuration. Attachments may be of any type; a fixed document-format allowlist is not a prerequisite for receiving and storing email. Arbitrary attachment support means preserving and delivering the bytes, not claiming that every format can be interpreted or inspected.

Filtering and application routing are optional capabilities that teams can adopt gradually. All optional filtering starts disabled for newly configured inboxes, including spam and malware checks; administrators explicitly enable the checks they need. Document-format filtering and application routing remain opt-in. The previously agreed checking, quarantine, ZIP inspection, and rule-based delivery policies apply when their corresponding features are enabled. A check disabled by policy is distinct from an enabled required check being unavailable: the latter still holds mail and retries under the agreed bounded retention policy. Basic protocol validity, authentication, authorization, tenant isolation, storage durability, and resource limits remain separate requirements.

Business document exchange remains the purpose, but existing applications expect an email system designed for human mail users and must not need immediate rewrites to use FRY. Conventional shared IMAP mailbox state is the default; independent per-application views are optional. Configuration granularity, administrator permissions, policy changes for already accepted mail, and migration between modes remain open. This decision supersedes earlier unconditional wording requiring filtering or application routing for every inbox.

Milestone scope: these optional capabilities are deferred until after the first production milestone proves conventional email operation. See [milestone sequencing](0014-prove-conventional-email-first.md).
