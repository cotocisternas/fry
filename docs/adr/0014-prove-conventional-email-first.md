# Prove conventional email operation before optional processing features

The first production milestone will prove conventional email operation for existing integrations: direct SMTP reception, durably queued outbound submission with FRY-owned retries through a shared default SMTP relay or an organization-specific last-mile MTA override, independent-copy external IMAP collection from configurable source folders with configurable destination-folder mappings, shared-mailbox IMAP access, isolated organizations with custom domains and addresses, optional per-domain catch-all inboxes and distribution aliases to multiple inboxes within an organization, distributed persistence, and the selected deployment-profile guarantees. Arbitrary attachments work without document classification. Mailbox lifetime and receipt-based recovery retention follow the agreed independent lifecycle rules.

Optional filtering (including spam/malware and document inspection), application routing, and application delivery features move to later milestones. These include rule-based fan-out, fallback applications, independent application views, and application-facing API/webhook delivery with separate acknowledgments. Their agreed behavior remains documented as future scope rather than first-milestone acceptance criteria. The first milestone also requires a web administration interface alongside an administrative API and CLI for managing organizations, domains, mailboxes, and credentials. These management interfaces are distinct from the deferred application-delivery API; both central FRY operators and organization managers restricted to their authorized organization scope are required. Explicit permission to open or download complete emails is available to organization managers for mail within their authorized organization scope and to central operators, with content access recorded in an audit log. Administrator sign-in must support both FRY-managed accounts and single sign-on in this milestone. SSO support uses generic OpenID Connect (OIDC); initial operation will use FRY-managed accounts, but OIDC support must be available in the first milestone. No specific provider or SAML requirement has been selected. One shared OIDC provider per independent FRY installation is sufficient initially. First OIDC login automatically provisions accounts and access from configured group/claim mappings. Explicit mappings may grant global-operator privileges. Organization managers are internal Customer Satisfaction and Professional Services staff; global operators are Technology and Development staff. Organization managers are restricted to explicitly assigned organizations, potentially several per person. Only global operators and their configured OIDC mappings may grant or revoke manager assignments; managers cannot delegate access. Assignment workflows and exact claim mappings, subsequent access changes, remaining permissions, audit details, and workflows remain open.

This sequence lets FRY validate its storage, throughput, conventional-client compatibility, and recovery model before teams adopt the additional integration features. It does not relax isolation, authentication, protocol correctness, or the guarantees of a selected deployment profile. The first production rollout must import existing mailbox history and state, including folders, message dates, and read/unread flags, for cutover. A planned final cutover pause is allowed after background copying, with affected clients paused and arrivals queued or deferred during final synchronization and switching; the pause is limited to 30 minutes for affected mailboxes, excluding background copying. Coordinated client checkpoint reset and resynchronization are acceptable, so source IMAP identifiers need not be preserved. Mail reception and mailbox access must resume within the 30-minute cutover limit; client resynchronization may continue afterward. Migration mechanics, resynchronization procedure, exact compatibility coverage, capacity acceptance criteria, and recovery implementation/validation still need definition. AWS is selected for the first rollout, with Kubernetes preferred subject to feasibility; the initial profile is one AWS region across multiple availability zones. São Paulo (sa-east-1) is the reference region for the first deployment and cost estimate. EKS, number of zones, and persistence backends are not yet selected. The first profile must survive one entire availability-zone failure without losing accepted email and resume mail reception and mailbox access within five minutes; this remains a target to validate. Whole-region-loss recovery belongs to a later profile. No library or backend is selected by this milestone decision.

Existing applications can use new FRY-issued usernames/passwords for IMAP and SMTP submission in the first rollout. Existing identity-system integration is not required for IMAP/SMTP application authentication. Separately, administrator sign-in must support both FRY-managed accounts and SSO in this milestone; generic OpenID Connect support must be available even though initial operation uses internal accounts. One shared OIDC provider per installation is sufficient initially; provisioning workflows remain open.
