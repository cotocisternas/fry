Why this replaces the NFS arrangement

No maildir/mbox tree shared between application servers. Bodies live in S3; folders, flags, identifiers, references, and work live in the database. Multiple workers can process different messages without sharing a filesystem.

1 · ADDRESS RESOLUTIONResolve recipients inside the owning organizations

Apply configured addresses, distribution aliases, and optional domain catch-all. Store relevant envelope recipients separately from headers. Reject unknown recipients when no catch-all exists.

2 · ORIGINAL BYTESStream the complete message into S3

Use bounded buffers and an immutable receipt identity. Large attachments do not require every worker to hold the entire email in RAM. An uploaded object alone is not an accepted receipt.

3 · RECOVERABLE RECEIPTCommit message metadata and pending work together

The database transaction records the original reference, destination inboxes, receipt time, and recoverable work. Do not hold a database transaction open while uploading the full message.

4 · ACCEPTANCE POINTNow return the final SMTP success reply

Only after object durability and database commit meet the active profile. If the database cannot commit, FRY cannot accept—even if object storage is healthy.

5 · MAILBOX AVAILABILITYWorkers materialize one entry per destination inbox

Use bounded, retry-safe batches. Several aliases reaching the same inbox within this submission produce one entry. Parallel receipt and body processing stay outside the IMAP owner's short state-update path.

S3 and PostgreSQL are not one atomic transaction. Orphan objects and ambiguous commits need reconciliation. If SMTP success is lost, the sender may submit again: no exactly-once SMTP promise.

Filtering, ZIP inspection, quarantine, and application routing are later milestones. The conventional email path works without them.

Shared IMAP mailbox

NLB → authenticated frontend → active mailbox/account owner. The owner coordinates concurrent sessions. PostgreSQL holds persistent UIDs, folders, flags, memberships, and changes; S3 supplies bodies.

Ownership and takeover

Use an authoritative lease and fencing epoch. Validate ownership atomically with mutations. A failed owner may disconnect clients; a replacement rebuilds state and preserves identifiers.

Deletion is a reference change

Expunging a mailbox entry does not automatically destroy the original. Keep it while another mailbox, pending work, or recovery period needs it. Old mail left in a mailbox remains usable.

Outbound SMTP queue

Authenticate and check authorized sender identities. Persist bytes and queue state before accepting. Workers hand off to the selected default or organization MTA, tracking per-recipient outcomes.

Bounded retry, visible failure

Retry temporary failures until the configurable deadline. Notify the sender and record terminal failure. Relay acceptance is separate from final recipient delivery; a lost reply can cause a duplicate retry.

IMAP collection

Map each selected remote folder to a FRY folder. Persist copies and checkpoint progress safely. Later remote reads, moves, or deletions do not mirror into FRY. Source cleanup stays opt-in.

Proposed initial work queue: PostgreSQL tables with short claims, leases, and idempotent completion. No separate broker yet. Add one only if measured queue/fan-out behavior requires it, while preserving the committed receipt ledger.

Agreed target: survive one entire AZ failure without losing accepted email; restore mail reception and mailbox access within five minutes. Whole-region loss is outside this first profile.

INTENDED RECOVERY · NOT A TEST RESULT1. Surviving compute handles new connections

Load balancers use healthy targets. Failed IMAP sessions reconnect. Enough capacity must already be available in the remaining zones.

2. Durable state survives and ownership changes safely

S3 retains originals. RDS promotes its standby if needed. Workers reconnect, fence old owners, reclaim expired work, and restore mailbox access.

3. Track reduced protection explicitly

The agreed policy allows continued acceptance with alerts once safe ownership and surviving durable storage exist. It never permits success while the authoritative database is unavailable.

Benchmark gate: database and hot inbox

A standby adds failover protection, not another writer. Start the spike with one database pair; measure whether production needs shards. One inbox can receive 500,000 messages, so spreading other inboxes across pods is not enough.

Library gate: Proton Gluon

Gluon remains a candidate. Its process-local state, default SQLite, cleanup behavior, and large-mailbox costs need adaptation and tests. Compare it with an alternative Go IMAP backend before choosing.

Cost and scope

The prior estimate priced six workers and one database pair as examples. This proposal additionally identifies a web ALB and secrets/telemetry services. Shards, traffic, and burst headroom can raise the subtotal. No resource count is proven production sizing.

Research: EKS TCP/NLB · S3 durability · RDS Multi-AZ · RDS failover. These building blocks do not prove FRY's throughput or five-minute recovery.
