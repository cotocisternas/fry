HOT ORIGINAL BYTES

Two durable copies in distinct AZs

Bounded staging → append records → fsync. Three storage members across three AZs is the starting placement proposal. Each receipt uses two.

Hash by receipt ID so one inbox can use multiple writers. Persistent disks; no shared NFS mailbox tree.

ONE METADATA AUTHORITY

PostgreSQL / RDS Multi-AZ

Receipt and envelope, byte locations, mailbox state, references, job epochs, reader pins, and cleanup obligations.

Short guarded transactions. No custom Raft groups or separate projection database in FRY.

Return SMTP success after both durable byte placement and database commit.

Mailbox publication can proceed before S3 upload. Lost responses are resolved by attempt identity; separate SMTP submissions can still duplicate mail.

↓ Background workers build and publish immutable packs
PACKED S3 STORAGE

64 MiB target / 60-second close candidate

Conditional PUT → verify → commit the pack index. Keep hot copies until publication is durable. Large originals use dedicated packs.

Read one message through its byte range; preserve raw email bytes. Pack size, fill, and worker capacity need measurement.

SAFE RECLAMATION

Preserve live references

Rewrite surviving records when a mixed pack contains expired mail. Retire old data after readers close. Track every hot, staged, and uploaded copy.

Permanent empty S3 markers prevent late create-only uploads from recreating retired bodies. Marker/catalog growth is a cost.

The normal target is no accepted-mail loss and recovery within five minutes after one AZ fails. Actual AWS fault tests are still required. Inaccessible storage can cause an overdue cleanup deadline; FRY must report it rather than claim deletion.

Choose a removed safeguard to inspect the failure sequence:

    This model assumes atomic database transactions, conditional object writes, and truthful durability confirmations. It covers one receipt, two AZs, one pack key, two worker epochs, and one reader. It does not validate real disks, PostgreSQL, S3, throughput, recovery time, or 24-hour cleanup.

    Implementation sequence

    1. Local append format, bounded staging, fsync/restart recovery, checksums, and range reads.
    2. PostgreSQL receipt guards plus two-member byte replication and injected failures.
    3. S3 conditional publication and retirement tests against the real provider.
    4. Compaction, reader cancellation, capacity limits, and repair.
    5. SMTP/IMAP integration, concentrated-inbox load, full AZ failure, and migration tests.

    Provider foundations: PostgreSQL locking · S3 conditional writes · RDS Multi-AZ. No infrastructure was provisioned.
