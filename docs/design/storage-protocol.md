# FRY storage protocol — implementation draft

Status: engineering proposal following the completed architecture interview. This specifies the simpler FRY-owned storage direction; it is not production code or a proven service-level guarantee. [Requirements](architecture-brief.md), [overview](replicated-hot-storage.md), [primary-source foundations](../research/storage-protocol-foundations.md), [verification plan](../validation/storage-failure-validation.md).

## One authority and a small interface

The `receiptstore` Go module owns acceptance, exact original bytes, locators, publication, and lifetime. Callers use `Accept(ctx, envelope, stream, attemptID)`, `Open(ctx, authorizedReceipt, range)`, and `ReleaseReference(ctx, referenceID)`. `Accept` includes the database receipt/work transaction: protocol callers must not independently assemble successful storage and metadata operations. A retry/status operation resolves an ambiguous `attemptID`; transport timeout is not evidence that acceptance failed. A source-collection adapter passes its checkpoint identity so checkpoint advancement and accepted receipt can commit together. SMTP attempts use generated IDs, never Message-ID for deduplication.

PostgreSQL remains the authoritative metadata adapter. Separate internal adapters handle hot byte records and S3 pack operations. No public document service, per-shard Raft state machine, Pebble dependency, or SCRAP code. Different Go process roles may use this module in one codebase. The module hides durable byte placement and cleanup from SMTP, IMAP, and administrators.

## Proposed starting parameters

These are adjustable engineering defaults for the first spike, not new business commitments:

- Three AZs and at least one hot-storage member in each. Normal acceptance requires two durable copies in distinct AZs. Dedicated EBS gp3 volumes are a candidate; container writable layers and instance replacement are not persistence.
- A fixed catalog of 1–16 ingestion shards selected from a versioned hash of the generated attempt ID, as recorded in [ADR 0016](../adr/0016-freeze-ingestion-placement-catalog.md); persist placement and exact member/file locations before dispatch. Each shard owns an independent pair. Shards distribute work, not mailboxes or organization authorization. Static assignment initially; no automatic rebalancer. The bound is an implementation limit, not a selected production count; actual count must be benchmarked.
- Packs target 64 MiB and close after at most 60 seconds, with an independently bounded scheduler delay. Scope pack builders by organization and compatible retention policy; actual occupancy can be much lower than the target. A message larger than the target uses a dedicated pack; initial format exercise includes 200 MiB without deciding the final SMTP limit.
- Single-request S3 PUT from a seekable staging file, with conditional creation. Initial packs are capped at 256 MiB; no multipart upload in this initial protocol. Backpressure covers staging space. Larger-message requirements require a new size policy, not silent truncation.
- DB work claims expire after 60 seconds and renew while active. Takeover increments an epoch. A worker can continue physical I/O after losing ownership, but cannot publish it. Clock checks use the database's current wall clock after obtaining locks.
- Body reads use renewable, bounded pins with a five-minute maximum overall lifetime for the spike. Cleanup stops new pins when retiring a location. Slow readers must close/retry rather than indefinitely pin expired content. This timeout needs legacy-client validation.

The agreed six-hour upload-outage buffer, configurable 24-hour active-storage cleanup, and advisory organization quotas remain in force. Proposed 30% capacity headroom and one hour of normal hot occupancy are cost assumptions, not measured needs.

## Authoritative records and locking

A minimal logical schema (not SQL DDL yet):

- `ingest_attempt`: ID, state `preparing|accepted|aborted`, lease deadline, epoch, expected envelope/destination snapshot, digest/length once known. Register before issuing byte writes. Never infer authorization from the absence of a row.
- `receipt`: ID, organization, durable-receipt time, digest, raw length, availability/lifetime state, manifest version, recovery deadline, protection mode/epoch. Recipients and source identities have explicit child records.
- `reference`: mailbox, pending work/delivery, or recovery ownership. Unique stable reference identities; acquire/release must lock the receipt guard row. A cached reference count is not an independent authority.
- `location`: receipt, hot member incarnation/file/offset or pack key/offset, encoded length, digest, generation, state. Publication and retiring locations are transactional.
- `ingest_target` and `hot_file`: every dispatched member/incarnation/operation ID, plus file inventory and state `open|sealed|rewriting|retiring|removed`. Register possible write destinations before dispatch, not merely after receiving locators. Include staging, repair, and compaction targets in the same obligation inventory.
- `pack_attempt`: unique attempt/key, worker epoch, membership snapshot, state `building|published|abandoned|retiring|retired`, integrity data. Register the key before issuing PUT. Replacements use new IDs and keys.
- `read_pin`, `work`, `cleanup`: bounded reader leases, retryable work, and durable deletion obligations including unresolved/offline copies.
- `protection_profile`: current epoch, normal/degraded status, eligible distinct failure domains and operator-visible reason.

Transactions modifying a lifecycle lock its guard row, then relevant rows in a stable order. Recheck epoch, state, deadlines, current references, and publication version after locking. Cleanup and acceptance contend on the same attempt/receipt guards; publication and retirement contend on the same pack guards. READ COMMITTED snapshots alone do not fence missing rows, expired workers, or reference creation. Retries handle deadlocks without repeating external effects blindly. Network and disk I/O never run while a database row lock is held.

Lock order: profile/ingest-attempt guards where applicable, receipt guards sorted by ID, container guards (hot file or pack attempt) sorted by type/ID, then location/job/pin rows. Resolve candidate IDs before the transaction, acquire guards, and recheck the manifest; if the set changed, retry from the start. Pack publication, abandonment, and retirement share the pack-attempt guard. Read-pin acquisition locks the receipt and selected container, rechecks live state/current location, and inserts the pin in that transaction. Renewal uses the same guards and refuses expired pins, retired containers, or exceeded overall lifetime. A renewed lease cannot revive a location after reclamation.

## Receipt protocol

1. Insert a `preparing` attempt, register each destination member/incarnation/operation ID, and reserve bounded local/staging capacity before dispatching bytes. Resolve destinations into a snapshot. Addresses rejected during SMTP RCPT are not resurrected later. A configuration change cannot silently redirect a durably accepted receipt.
2. Stream to two selected storage members over authenticated internal connections. Each member writes an attempt-scoped temporary file, validates framing/length, and appends the completed record to one of its own append files. This staging costs additional disk I/O but keeps slow SMTP streams from monopolizing shared append writers. Large records may occupy a dedicated sealed file. Hot copies have independent offsets.
3. Members return authenticated durable locators only after record bytes/footer and required directory entries are durable. Group fsync may batch completed appends, but no member acknowledges a record before its batch is synced. Every member/file incarnation is immutable; a replacement disk gets a new identity. One live writer per volume is required (single-attach configuration plus process lock); Kubernetes RWO alone is not proof of writer exclusion.
4. With both confirmations, lock the attempt and protection guard. Recheck its epoch/deadline, digest agreement, byte placement, and state. Atomically publish the receipt, locations, destinations, recovery reference, pending mailbox work, and collection checkpoint where applicable. Commit under synchronous metadata durability. Set the durable receipt timestamp here.
5. Only now return storage success and final SMTP `250`. Availability work can create the mailbox independently of S3 upload. For lost replies, query by the stable attempt ID; do not delete uploaded bytes until the authoritative state is resolved.

Member durability receipts prove completed durable writes, not that nodes will remain healthy. Distinct-AZ placement supplies normal single-AZ tolerance; health events mark repair debt. A profile change during receipt forces a post-lock placement recheck. Degraded acceptance records its actual protection and requires database authority plus a healthy durable byte copy. Continue automatically under the agreed policy after safe activation, with alerts, never by bypassing the database. Normal metadata recovery is a managed database responsibility; it is not another FRY election protocol.

An expired preparation is first atomically moved to `aborted`. That state prevents acceptance from racing cleanup. Keep an identity tombstone until every registered byte location/staging obligation is settled; late member writes are unaccepted cleanup debt. A hot member seals files under its local writer lock before deleting them; an abandoned writer cannot append into a file already reclaimed by that same member. Unreachable members are fenced from serving until reconciliation on return.

Each member registers active operations under a local per-attempt lock before accepting the stream, checking the authoritative attempt/target generation. Cleanup sends cancellation to every preregistered target. Under that same local operation lock, cancellation prevents new appends for the attempt, stops active streams, and waits for their handles to close. A queued retry rechecks the terminal database state and is rejected; after restart the database is checked before admitting any new operation. `cancel_confirmed` establishes quiescence, while `bytes_removed` is a separate completion after staging deletion and append-file reclamation. Never mark cleanup complete on cancellation alone. Offline targets remain recorded and cannot silently disappear from the inventory.

## Pack publication and late upload safety

A pack worker claims accepted records, pins their sources, and registers a fresh pack key and membership snapshot. It builds an immutable seekable pack and verifies individual records. It PUTs with `If-None-Match: *`, using S3 checksums rather than treating ETag as a universal content hash. An ambiguous upload is resolved against the expected key, size, checksum, and manifest identity. HEAD alone does not validate arbitrary payload content unless the stored checksum is meaningful and verified.

After upload, lock the job and affected receipt guards in stable order. Recheck ownership epoch and every source manifest/reference. Publish the verified pack and new current locations atomically, with durable cleanup work for superseded copies. If a member became unneeded while the pack was built, discard that attempt and rebuild eligible membership; do not publish expired records and restart their cleanup clocks. Batch sizes bound transaction time. A newly built pack may contain at most the configured byte/member limit.

A database lease cannot cancel a PUT already in flight. The initial S3 adapter therefore uses a **never-versioned pack bucket** and keys that are never reused. All producer writes are conditional creates; producer credentials cannot overwrite or delete. For retirement, the cleanup identity conditionally replaces the object's body with an **empty permanent tombstone**: use If-Match for the observed object, or If-None-Match when absent, retrying conflicts. An old create-only PUT either wins first and is overwritten, or loses to the tombstone. No mail content or sensitive metadata is copied into that marker. A marker is an actual object, not an S3 delete marker.

Retire DB publication rights before replacing any body. Retain the marker permanently in this version of the protocol; no Lifecycle rule may delete it. This deliberately spends a small object and catalog record per retired key to prevent resurrection without inventing cross-system transactions. Enforce conditional-create policy and separate cleanup permissions. This is an inference from documented S3 atomic conditional writes and needs an integration test, not a claim that it has been tested here. Versioned/suspended buckets and alternate S3-compatible providers require separately validated adapters. Multipart and CopyObject are outside this initial producer path.

## Format and reads

Use a versioned self-describing pack: a small pack header, then independent message records containing receipt ID, length, whole-message SHA-256, and payload frames. Proposed frame payload is 64 KiB with CRC32C per frame; small fixed record headers and frame overhead must be included in actual sizing. Preserve raw RFC message bytes; reconstruct payload without reserializing MIME. Independent records permit aligned range reads; no whole-pack compression initially. DB offsets reference the encoded record, with enough information to calculate aligned frame ranges.

On hot-member restart, scan the valid record prefix, checking receipt/attempt identity, member/file generation, encoded bounds, frame order, footer, and checksums. Truncate only an incomplete unacknowledged tail while holding exclusive file ownership and after reconciling accepted locators; an interior failure is quarantined/repaired, never treated as permission to truncate later acknowledged records. Validate those identities and bounds on reads too. Full reads verify SHA-256 as well as per-frame CRC; partial reads verify the selected frames and make no claim of validating unread bytes. A final digest failure aborts the operation and records repair debt even if earlier verified frames were already streamed.

`Open` checks FRY authorization and lifecycle, then obtains a pin for the current location under its guard. Validate frame checksums before returning those bytes; a later error can abort the stream, which protocol adapters must handle by failing the transfer rather than claiming completion. The design does not promise whole-document all-or-error buffering. Range reads can require extra aligned bytes and GETs. On unavailable/corrupt hot data use another verified location, schedule repair, and never substitute unchecked bytes.

A pin prevents retirement while active, not reference expiry forever. Readers must stop/close when their pin expires or cannot renew. DB lease expiration does not close OS file descriptors: member-side handle ownership and cancellation are part of cleanup. Pins/handles from a partitioned process remain unresolved debt; do not declare erasure complete merely because unlink succeeded. New lookups after publication choose the new manifest; old locations remain until existing bounded reads drain.

## Reclamation and the 24-hour requirement

All reference creation/deletion and eligibility decisions lock the receipt guard. When the final reference ends, set an immutable eligibility timestamp and deadline; later retries, pack changes, and maintenance do not reset it. A new reference may be acquired only while the receipt remains live and the authoritative operation allows it; once retiring, restore must use an explicitly recoverable copy with a new lifecycle, not resurrect that row.

For a mixed-live pack, copy only still-needed records into a fresh pack, verify, then atomically swap those live locations and mark the old pack retiring. If membership/liveness changed since the copy, abort and retry rather than publishing stale contents. Drain bounded reads, replace the old S3 body with its empty tombstone, and reclaim corresponding hot/staging/cache copies. Maintain durable obligations for all historical locations, unpublished attempts, and partial copies until accounted for. A pack with no remaining live records skips rewriting.

Hot append files have their own reclamation path: seal on size/age or an approaching cleanup deadline, stop admission to that file, inventory every record, and resolve all preparing/aborted attempts. If needed live records lack a safe S3 successor, copy them to a new local file in the same AZ, fsync it, and conditionally publish replacement locators before retiring the old file. This replacement is not another AZ replica. A new receipt/reference/pin cannot attach to a retiring file. Remove it only after every record is accounted for and all actual handles close; unknown records trigger reconciliation. This also permits deadline-driven cleanup during an S3-upload outage while preserving live hot records.

Schedule by the oldest cleanup deadline, reserve rewrite capacity, and alert before/after missed deadlines. Cached originals are also active copies and must participate in expiry. Object versioning is disabled for this initial pack bucket so overwriting does not leave noncurrent email bodies. Database snapshots/backups have their own explicitly unresolved retention policy.

**Availability limitation:** inaccessible S3 or an offline disk can prevent physical cleanup within 24 hours. Record a deadline violation and outstanding copies; never claim success or delete live neighboring mail to hide it. Returning offline members reconcile and erase expired copies before serving. The specification cannot promise media sanitization or physical destruction of inaccessible hardware. Active-storage cleanup means removal of application-recoverable content through the configured storage mechanisms; stronger erasure obligations need a separate contract.

## AWS deployment and cost consequences

Use stateless protocol/administration workers separately from stateful hot members. The reference placement is one region/three AZs, EKS, NLB mail ingress, HTTPS admin ALB, RDS Multi-AZ, three hot members with persistent gp3 disks, and an S3 gateway endpoint. Use workload-scoped credentials, TLS, and encrypted disks/bucket. These are proposed choices, not provisioned infrastructure.

Six-hour capacity must be available above normal occupancy, with two copies, staging, repair, compaction, and post-AZ-loss headroom. Advisory organization quotas cause alerts; capacity-based flow control and fair scheduling still apply. Prioritize receipt durability and deadline-driven cleanup without starving reads. Bound upload and replication concurrency separately. A storage outage is not permission to delete accepted mail.

Same-region S3 transfer and cross-AZ application replication have different billing paths. The [revised model](../research/packed-storage-cost-estimate.md) explicitly prices replicated hot capacity, extra workers, and cross-AZ traffic. Packing can save request charges while increasing the total. Database row/WAL volume, one-inbox IMAP state, cross-organization fan-out, partial fetches, and actual pack fill remain sizing gates. No custom database sharding or broker is selected in this draft.

## Implementation sequence

Progress: step 1 has a first [local Go implementation and test report](../validation/local-hotstore.md). Step 2 now has [PostgreSQL authority and two local-member ingestion](../validation/replicated-receipts.md), with integration tests for publication, retries, stale generations, cancellation, and connection failure. Step 3 now has [packed-object upload/publication, cold reads, and unpublished-object retirement](../validation/packed-objects.md), exercised with real PostgreSQL and the AWS SDK against a local HTTP contract fixture. Actual S3 conditional-write and IAM tests remain outstanding. The later [authenticated replica transport](../validation/replica-transport.md) runs separate members with generation-scoped operations and verified streaming. HA metadata, coordinated unclean-process recovery, and degraded-mode operation remain outstanding. Step 4 now has [local lifecycle/reclamation code](../validation/storage-lifecycle.md), including bounded reads, references, pack compaction, hot-file replacement and scratch recovery. Its fixed read lifetime, conservative orphan pins and whole-member rewrite pauses are prototype limitations; online rotation, distributed repair and production-scale scheduling remain outstanding.

1. Implement one-process append format, bounded staging, checksums, real fsync/restart recovery, and range reads on temporary local disks; use synthetic data only.
2. Add PostgreSQL schema/guard transactions and two-member streaming receipt; inject ambiguous commit, stale lease, restart, and disk failures through the same module interface.
3. Add conditional S3 pack publication and permanent retirement markers; run real provider integration tests for concurrent PUT/retirement. An emulator is useful but not sufficient evidence for provider semantics.
4. Add compaction, reader cancellation, capacity budgets, repair, and cleanup deadline accounting. Run the [failure matrix](../validation/storage-failure-validation.md).
5. Integrate SMTP/IMAP and benchmark at retained-data scale, concentrated bursts, and surviving-AZ capacity. Reprice measured infrastructure, then test migration/cutover. This ordering avoids presenting a storage model as a working mail gateway.
