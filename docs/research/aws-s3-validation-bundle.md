# Minimal real-AWS S3 validation bundle

Researched 2026-10-18. This is a proposed disposable **synthetic-data** validation bundle, not executed AWS evidence. No credentials were loaded and no AWS resources were provisioned. Scope is the current adapter and its single-request pack uploads, not EKS deployment, throughput, AZ recovery, backups, or a production IAM attestation.

## Existing contract and smallest useful bundle

The current [adapter](../../internal/objectstore/s3.go) creates positive-sized pack images with `PutObject`, `If-None-Match: *`, explicit SHA-256, and expected bucket owner. It reads checksums/ETags with HEAD and verifies conditional byte ranges. Retirement HEADs the key, then writes an empty body with SHA256(empty), `x-amz-meta-fry-retired: true`, and either the observed ETag in `If-Match` or `If-None-Match: *` for an absent key. It resolves races/lost replies by rereading the marker. ETags are opaque comparison tokens, not FRY's content digest. `NewS3` refuses any nonempty versioning status or lifecycle rules; these are startup observations, not continuous drift protection.

Prepare locally before requesting account inputs:

1. A reviewed resource/policy template and an explicit plan/apply/cleanup separation. One unique general-purpose bucket in `sa-east-1`, two final application roles, and a separate provisioning/cleanup identity. No reuse of an existing bucket or FRY namespace.
2. An opt-in Go contract runner using the pinned SDK and actual `S3Config.Open`, plus raw SDK clients for deliberately forbidden requests. Fixed small corpus, random run ID/key suffixes under `packs/v1/`, bounded request count, byte count and deadlines; no SMTP/PostgreSQL deployment needed initially.
3. A bounded report containing source/module/policy hashes, region, expected account, effective role ARNs, operation/result/status/request IDs, image digests, and cleanup outcome. Never log authorization headers, temporary credentials, SSO caches, signed URLs, or message contents. Failure reports must preserve sanitized diagnostics and remaining-resource identifiers.

Use AWS's native regional endpoint: `region=sa-east-1`, `endpoint` absent, `use_path_style=false`, `loopback_anonymous=false`, explicit 12-digit `expected_bucket_owner`, and two explicit reviewed profiles. [Runtime configuration](../../internal/objectstore/config.go) loads the roles separately; different profile labels alone do not establish different effective principals. Record STS identity for each final session and reject equal roles or unexpected accounts before S3 writes. Expected-owner mismatch is independently specified to fail with 403. [GetBucketVersioning API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketVersioning.html)

## Bucket and credential preparation

Create the bucket fresh with versioning never enabled, no lifecycle, no replication, no Object Lock, no access points or external writers, and ordinary SSE-S3 default encryption for this first drill. Require empty versioning status; `Suspended` is not acceptable and cannot restore the never-versioned state. Keep before/after settings evidence. [Versioning states](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketVersioning.html)

Use Bucket owner enforced ownership and all four Block Public Access settings. This keeps ACLs out of the permission model and public grants out of this rehearsal. Do not introduce SSE-KMS in the first bundle: it adds independent KMS permission/checksum concerns without testing the minimum adapter contract. [Object Ownership](https://docs.aws.amazon.com/AmazonS3/latest/userguide/about-object-ownership.html), [Block Public Access](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html), [HEAD checksum permissions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html)

Authenticate the operator through IAM Identity Center (`aws sso login`) and configure two final assume-role profiles using the SSO profile as `source_profile`. Use separate role ARNs/trust and least-privilege policies; the source operator is privileged and is not an application identity. Do not create static IAM access keys, export session secrets into reports, or give producer permission to assume retirement/provisioning roles. SDK v2 supports SSO profiles; renewal of an expired SSO login still requires login. [SDK v2 SSO](https://docs.aws.amazon.com/sdk-for-go/v2/developer-guide/configure-gosdk.html), [Assume-role profile settings](https://docs.aws.amazon.com/sdkref/latest/guide/feature-assume-role-credentials.html)

## Enforceable policy envelope

Treat the following as a policy-generation specification, not an already tested policy JSON. Use exact role principals, exact bucket/object ARNs, and explicit bucket-policy denies as well as narrowly scoped identity allows; a conditional Allow alone can be bypassed by another applicable Allow. Explicit Deny takes precedence. Root/bucket-policy administrators and role-policy administrators remain trusted. [IAM evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html)

| Identity | Minimum positive permissions | Required restrictions |
| --- | --- | --- |
| Producer | `s3:PutObject`, `s3:GetObject` only on `BUCKET/packs/v1/*`; `s3:ListBucket` on the dedicated bucket | PUT must carry exactly `If-None-Match: *`; no overwrite with `If-Match`; no delete, config, ACL/tag alteration, or role escalation. |
| Retirement | `s3:GetObject`, conditional `s3:PutObject` on the same prefix; `s3:ListBucket`, `s3:GetBucketVersioning`, `s3:GetLifecycleConfiguration` on bucket | PUT must have `If-Match` or `If-None-Match: *`; no unconditional writes/deletes/config changes. It remains a trusted writer, as explained below. |
| Provisioning/cleanup | Only permissions needed to create/configure this isolated bucket/roles, inspect evidence, and finally remove them | Its credentials are not supplied to FRY or the contract runner's application clients. It performs destructive cleanup only after all writers stop. |

`ListBucket` is intentional: missing-key HEAD returns 404 only when the caller has it; otherwise absence may produce 403. Retirement must distinguish missing keys from forbidden access to create absent-key markers. Because HEAD has no list-prefix parameter, do not assume a `s3:prefix`-conditioned ListBucket grant provides this behavior; the minimal drill uses unconditioned ListBucket on its dedicated bucket. Object reads/writes remain prefix-limited. [HEAD authorization and missing objects](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html)

For PUT conditions, use explicit Deny for producer requests missing `s3:if-none-match`, and another for a present value unequal to literal `*`. Deny producer `s3:if-match` presence. Retirement denies requests where **both** conditional keys are absent; a present if-none-match must equal literal `*`. Reject both headers together in the bundle rather than depend on precedence. These separate statements avoid accidentally expressing OR as IAM's within-block AND. This envelope is supported by S3 conditional-write policy keys; `If-None-Match` expects `*`. [Conditional-write policy documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html), [PutObject header semantics](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)

Do not copy AWS examples' multipart exemptions into this bundle. The current adapter does not use multipart. Missing-condition denial should also prevent multipart initiation/completion and copy paths, rather than permit unpublished multipart debt. AWS documents that these exemptions are needed specifically for multipart stages; copy operations have distinct 403/501 behavior under conditional-write enforcement. [Conditional-write enforcement](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html)

Both application identities must be explicitly denied `s3:DeleteObject` and `s3:DeleteObjectVersion`. Restrict their effective S3 actions to the listed read/conditional-write set, including denial of bucket versioning/lifecycle/policy/replication/encryption/ownership/public-access changes, bucket deletion, and object ACL/tag changes. Pin role trust/attached policies so they cannot grant themselves broader access. Keep configuration changes out of every other automated writer during the drill. An administrator able to replace policies can defeat these protections; startup checks cannot close that trust gap. The official action names differ from API names, notably `GetLifecycleConfiguration` and `PutLifecycleConfiguration`. [AWS machine-readable S3 authorization reference](https://servicereference.us-east-1.amazonaws.com/v1/s3/s3.json), [reference format](https://docs.aws.amazon.com/service-authorization/latest/reference/service-reference.html)

### Marker enforcement: hard limit

The current retirement role can conditionally replace an existing object with **arbitrary content**, including replacing a marker after reading its ETag. The conditional policy proves compare-and-swap, not authorized retirement, empty content, or marker permanence against that role. Producer restrictions prevent a delayed producer from replacing a marker; they do not make the retirement credential harmless.

AWS's current S3 action/condition-key inventory has no `x-amz-meta-fry-retired` or general user-metadata equality key, no PutObject `Content-Length` condition key, and no `x-amz-checksum-sha256` condition key. Object tagging keys do not inspect user metadata. Thus do not invent a policy requiring this adapter's metadata or literal zero Content-Length. `content-length-range` belongs to browser POST policies, not an IAM condition for this SDK PutObject path. This absence is an inference from the published authorization inventory, not proof about undocumented features. [S3 authorization inventory](https://servicereference.us-east-1.amazonaws.com/v1/s3/s3.json), [metadata versus tags](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingMetadata.html), [POST policy conditions](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-HTTPPOSTConstructPolicy.html)

Possible future hardening deserves a separate experiment: `s3:x-amz-content-sha256` is a documented payload-signing condition key. Requiring the signed SHA-256 of the empty body could constrain retirement payloads if exact-hash matching and the chosen signing mode are verified; this is **not** the adapter's explicit checksum header, and does not enforce `fry-retired` metadata. AWS documents unsigned and streaming payload modes, so merely supplying SHA256(empty) as `ChecksumSHA256` does not establish that policy. Do not add this restriction to the baseline policy or claim it works with the current adapter without an actual wire/policy test. [SigV4 policy keys](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/bucket-policy-s3-sigv4-conditions.html), [payload signing modes](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-auth-using-authorization-header.html), [streaming checksum modes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html)

Consequently the first bundle can validate **trusted retirement code plus IAM-limited producer behavior**. A requirement that IAM prevent a compromised retirement role from resurrecting a marker remains unmet. Stronger separation needs a constrained retirement service or a deliberately revised storage/security contract, not an assertion that metadata policy exists.

## Concrete test matrix

Run successful control calls with each intended profile first, so a broken credential or wrong endpoint cannot satisfy every negative test. Preserve AWS error code **and HTTP status**, not only FRY's translated error. Bound retries; IAM propagation is not a reason to accept a generic failure as success.

| Test | Required result/evidence |
| --- | --- |
| Effective identity and settings | Distinct intended role ARNs/account; correct region/owner; never-versioned/no-lifecycle settings; actual `S3Config.Open` succeeds. Wrong expected owner fails 403 without mutation. |
| Create/HEAD/range | Actual adapter creates small deterministic image; HEAD returns correct size/SHA-256 and opaque ETag. Exact and clipped valid ranges match expected bytes using If-Match. Wrong ETag is a conditional conflict, not an authorization success/failure substitute. |
| Duplicate create | A second valid conditional create on the same key fails 412 (adapter ErrConflict); original bytes/digest unchanged. |
| Producer unconditional PUT | On a known existing key **and** a fresh key: authenticated well-formed unconditional request fails 403 AccessDenied, never 412. Existing image remains unchanged; fresh key absent. |
| Producer overwrite | Correct known ETag with If-Match only must fail 403; otherwise a stale ETag could produce 412 and hide excessive permissions. |
| Retirement conditional requirement | Well-formed unconditional fresh/existing PUT fails 403. Normal adapter Retire(existing) and Retire(absent) succeed; repeated Retire is idempotent. HEAD marker has metadata=true, size0, SHA256(empty). |
| Delayed producer | Valid If-None-Match `*` after retirement fails 412 and cannot resurrect bytes. Controlled producer-versus-retirer races end with a verified marker after retirement completes; report actual 409/412 outcomes rather than demand one race ordering. |
| Delete prevention | Both roles DeleteObject on existing image **and existing marker** fail 403; verify both remain. Never count a missing-key delete or a 412 as a deletion-denial test. |
| Configuration/escape prevention | Both roles' valid version-enable and lifecycle-write attempts, writes outside packs/v1/, and attempts at omitted write/role-escalation permissions fail AccessDenied. Unexpected version-enable success fails the run permanently: do not suspend it and continue. Keep such tests confined to this disposable bucket. |
| Integrity | Deliberately incorrect supplied SHA-256 is rejected; all successful reads match the local corpus. Validate retirement safety via ordinary adapter code; do not claim a malformed-marker raw PUT is IAM-denied. |

The expected 412 and conflict race behavior comes from conditional semantics, whereas the forbidden operations above must be denied by authorization. [Conditional write behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [checksum validation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html)

Avoid destructive drift tests against shared resources. To validate adapter startup refusal for already-versioned or lifecycle-enabled buckets, use separate freshly provisioned disposable negative buckets, if that coverage is included; never enable versioning on the primary contract bucket and then describe it as never-versioned.

## Cleanup, evidence, and adoption gate

Stop/join the runner and every producer/retirement writer first; no background FRY worker may retain these credentials. Then the separate provisioning identity removes the application writer access, inventories the exact disposable bucket, removes synthetic images **and marker objects**, verifies emptiness, and deletes the bucket and dedicated role/policy resources. Do not give DeleteObject to the application roles to simplify cleanup. Final success requires checked cleanup; on failure retain identifiers and a resumable explicit cleanup plan, not secret credentials. If an unexpected test enabled versioning, cleanup must enumerate/remove versions and delete markers too. [Emptying a bucket](https://docs.aws.amazon.com/AmazonS3/latest/userguide/empty-bucket.html), [deleting a bucket](https://docs.aws.amazon.com/AmazonS3/latest/userguide/delete-bucket.html)

The bundle must report policy/settings before and after, exact raw negative outcomes, all content checks and cleanup separately. It establishes only this account/region/SDK/policy combination at test time. It cannot establish permission separation merely from profile names, protection against trusted administrators or a malicious retirement role, production retention/deletion guarantees, AWS restore readiness, sustained throughput, or AZ-failure recovery.

Inspection baseline: `go.mod` pins SDK core v1.47.3, S3 v1.114.3, config v1.33.9; [pinned PutObject source](https://github.com/aws/aws-sdk-go-v2/blob/service/s3/v1.114.3/service/s3/api_op_PutObject.go) distinguishes checksum fields from payload signing. The official machine-readable S3 reference was fetched without credentials on 2026-10-18: SHA-256 `cc1e013ec21e77693336485a3c0bf5c88395bfde40d81315e332640cd34137b2`. Its endpoint was readable with HTTPS curl while the browser tool could not render it; no secondary IAM claim was substituted.
