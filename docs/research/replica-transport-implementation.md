# Replica transport and member ownership

Investigated 2026-10-17 against FRY's current receipt/member/lifecycle code, PostgreSQL 18 documentation, and Go `net/http` and `crypto/tls`. The inspected Go source is `/home/coto/.local/share/mise/installs/go/1.27.2/src`; API choices should still respect FRY's declared toolchain minimum. This is engineering research, not a demonstrated distributed-durability or AZ-failover guarantee.

## First fix ownership; transport alone is insufficient

Current `LocalMember` owns one local root lock, hot-store incarnation, operation registry, and read/write gate. `write` validates SQL authority under an attempt stripe, registers active work, appends/fsyncs, then publishes the locator. `cancelAttempt` checks terminal SQL state under the same stripe, cancels/closes input, waits for the operation's done channel, and only then confirms cancellation. `ReclaimHot` excludes member operations while replacing its local generation. These local invariants must survive a process boundary. [Member implementation](../../internal/receiptstore/member_linux.go), [acceptance authority](../../internal/receiptstore/postgres.go), [hot reclamation](../../internal/receiptstore/hot_cleanup_linux.go).

A filesystem flock proves exclusion on that locked local inode. It does **not** prevent a different machine from opening a copied disk with identical member and file IDs. A PostgreSQL advisory lock does not establish that the previous process stopped writing its disk after its database connection died. Therefore: **do not automatically reuse a logical member/disk identity or clear old-generation obligations merely because a new process obtained a lock.** Fixed, explicitly registered disks and conservative unresolved ownership are a useful first process-transport scope. Automatic takeover needs additional trusted fencing or proof of prior process/volume shutdown. [FRY storage protocol](../design/storage-protocol.md#receipt-protocol), [PostgreSQL advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS).

## Small interface/refactor

Keep storage and SQL publication inside the member process. The coordinator should address an opaque member descriptor, not reach through `m.bytes`, `m.gate`, or compare pool pointer identity. Suggested conceptual interface:

| Operation | Contract |
| --- | --- |
| Describe | Registered installation/member ID, owner generation, file incarnation, failure-domain label, protocol version; SQL validates these values |
| Write | Attempt/receipt/org IDs, attempt/profile epochs, expected member owner/file generation, and streamed bytes; success only after durable append and authoritative locator recording |
| Cancel | Terminal attempt plus exact owner generation; returns only after that owner's active writes and staging cleanup have stopped and cancellation has been durably recorded |
| Read | Unique read-operation ID, authorized receipt/pin, expected locator/file incarnation, bounded range; stream with explicit validated completion |
| Read status/close | Owner-specific confirmation that the actual read/file handles closed; timeout is unresolved debt |

These are semantic operations, not a mandatory new public API. Keep local and HTTP adapters behind the same narrow member interface. Initially keep hot rewrite/reclamation inside the owning member; do not expose remote filesystem paths or let the coordinator delete files. Existing `prepare`, `recordCopy`, read selection, and cleanup routines need explicit descriptor/owner arguments rather than `*LocalMember` internals. [Store coupling](../../internal/receiptstore/store_linux.go), [local lifecycle](../../internal/receiptstore/lifecycle_linux.go).

## SQL owner generations and lock ordering

**Proposed additions:** a durable owner generation and unique boot identity for each member, captured in every registered target and read obligation before external I/O. `prepare`, `validateTarget`, `recordCopy`, and cancellation confirmation check the relevant generation. Preserve historical obligations instead of overwriting them during replacement. A new owner must not confirm an old owner's unfinished cancellation or read closure. Verified accepted bytes from an unchanged file incarnation may remain readable under a new authorized read owner, but that does not prove old writes/handles or cloned media are gone.

Use a session advisory lock only for active-owner admission and diagnostics, on a dedicated PostgreSQL connection. Never acquire it through one pooled query and release that connection back into general use: session locks persist until explicit unlock or session termination, independently of transaction rollback. A new connection must acquire ownership afresh, not assume reconnect preserved it. An uncertain/lost ownership session must stop new admission and begin cancellation; keep old obligations until closure is proven. [Session versus transaction advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS).

The lock is not a storage fencing token. Connection termination can release the database lock while the old process still holds file descriptors, is paused in fsync, or has not observed the partition. Generation checks can prevent stale metadata publication when all writers consult the same authoritative database; they do not retract disk writes. Database failover must preserve committed fencing state and exclude an old writable primary. PostgreSQL asynchronous replication alone does not ensure this. Never claim a session advisory lock survives promotion as durable ownership state. [Replication and failover requirements](https://www.postgresql.org/docs/18/warm-standby.html).

Preserve FRY's SQL ordering: profile/attempt guards, sorted receipt guards, sorted member/container guards, then target/job/pin rows. A new owner-registration transaction should not hold a member row and then wait for an attempt row held by an ingest/rewrite transaction that needs that member. Read current owner generation again under the publication guard rather than relying on an earlier request check. The local order is member gate, attempt stripe, SQL checks; do not reverse it in a cancellation callback. [Documented lock order](../design/storage-protocol.md#authoritative-records-and-locking), [existing publication](../../internal/receiptstore/postgres.go).

Ownership-loss handling must cancel streams **before** waiting for the exclusive member gate. Calling `gate.Lock` first can wait forever behind a writer holding `gate.RLock` while blocked reading input. Stop admission through a thread-safe terminal state, cancel active operations through their registry, close input/transport as required, wait for done, then close storage and release local ownership. Do not wait for network or disk I/O while holding SQL row locks. Fsync may remain uninterruptible; cancellation acknowledgment must wait rather than misreport quiescence.

## mTLS and request admission

Use HTTPS with `tls.Config.ClientAuth = tls.RequireAndVerifyClientCert` and explicit `ClientCAs`; clients verify the server through `RootCAs` and expected `ServerName`. Keep `InsecureSkipVerify` false. Map a verified certificate identity to an explicit installation/member/coordinator role and operation allowlist; possession of any certificate from the same CA is not authorization for every operation. Bind requested target and owner generation to SQL, never to caller-supplied labels alone. `VerifyConnection` runs after normal verification, including resumed TLS sessions; `VerifyPeerCertificate` has different resumption behavior. [TLS configuration](https://pkg.go.dev/crypto/tls#Config).

Certificate checks happen at handshake, so existing pooled connections also need request-level checks against current allowed identities/generations. Configure redirect refusal, explicit trusted endpoints, and no environment-proxy inheritance for this internal transport unless intentionally supported. Avoid transparent compression so byte counts and integrity remain clear. Bound header bytes, metadata sizes, concurrent requests, per-member byte reservations, handshake/header/body time, and response-body sizes. Use request contexts and server deadlines; HTTP acceptance of a connection is not storage admission. [HTTP server/client APIs](https://pkg.go.dev/net/http), [transport source](https://go.dev/src/net/http/transport.go).

## Write framing and ambiguous replies

A known Content-Length allows Go's HTTP reader to detect premature EOF, but an application must consume and check the complete body. `io.CopyN` of the declared payload length alone does not establish complete application framing. For unknown-length streaming, clean HTTP EOF proves transport completion, not that the source transaction intentionally completed. Never translate a producer error into a clean pipe Close. `ContentLength == 0` with a nonnil client Body can mean unknown length; inspect the API rather than using zero as a universal empty-message marker. [Request fields](https://go.dev/src/net/http/request.go), [HTTP truncation handling](https://go.dev/src/net/http/transfer.go).

**Proposed wire format:** versioned bounded payload frames plus a terminal record containing final byte count and SHA-256, written only after the original source returns successful completion. Include the registered claim identity in bounded metadata. The receiver enforces frame ordering, message-size limit, count/hash, terminal record, and actual HTTP body completion before exposing successful EOF to hot-store staging. Reject extra bytes, unsupported content encoding, malformed/truncated frames, and missing final records. This supports unknown-size SMTP streams without buffering 200 MiB in memory. Framing overhead must count toward transport limits separately from raw-message limits.

Member success requires `hotstore.Append` success **and** authoritative `recordCopy` success. HTTP 2xx alone is not receipt acceptance; coordinator `finalize` still verifies both distinct targets/digests/profile and commits receipt state. A lost HTTP response or uncertain SQL commit is resolved by attempt/target status using stable IDs, not by deleting the member's bytes. Retry only identical claim/operation content; do not permit automatic client replay to silently create another operation. Delayed old-generation requests fail the current target/owner checks. [Acceptance protocol](../design/storage-protocol.md#receipt-protocol), [append staging/fsync](../../internal/hotstore/store_linux.go).

## Reads need member-owned obligations and completion

Current `Store.Open` deletes its read pin only after the local storage call returns and handles are closed. A remote client's request cancellation or `Response.Body.Close` does **not** prove the server's read and file handles ended. Preserve a durable member-side read obligation keyed by read operation, owner generation, and file incarnation, registered under receipt/container guards before opening the file. Only that member owner clears it after the underlying read returns and handles close. A new owner cannot clear old-generation reads just because a deadline expired. If closure confirmation is lost, status reconciliation may clear the coordinator's obligation later; until then cleanup remains conservative. [Current pin release boundary](../../internal/receiptstore/lifecycle_linux.go), [read/cleanup requirements](../design/storage-protocol.md#format-and-reads).

**Confirmed HTTP pitfall:** a local Go server set `Content-Length: 3`, wrote and flushed `abc`, then panicked with `http.ErrAbortHandler`, simulating a storage check failing after the last payload byte. The client observed status 200, `abc`, and nil `io.ReadAll` error. Reproducer: `/tmp/fry-replica-research/http_completion.go`. Thus aborting after sending the declared bytes cannot reliably communicate late integrity failure.

Use a terminal application success record only after the storage read has completed all required integrity checks and released its handles. The client decoder verifies the range/identity/count and completion record; withhold its final payload chunk until this verification so a caller using CopyN cannot stop before learning of failure. For zero-length ranges, validate completion before returning the reader or any successful EOF. A missing success record is an error even if every payload byte arrived. Full reads retain whole-message SHA verification; partial reads verify touched frames and the requested range, without claiming unread-byte verification. Retry another replica only before any decoded payload reaches the caller. [HTTP body implementation](https://go.dev/src/net/http/transfer.go), [FRY hot read implementation](../../internal/hotstore/image_linux.go).

Cancel endpoints must validate terminal SQL attempt state under the same local registry lock as write admission, signal cancellation, unblock input, wait for active work/staging cleanup, commit generation-specific confirmation, and only then send success. HTTP timeout, connection loss, process death, database-session loss, and lease expiry are not cancellation acknowledgments. Erasure additionally requires all bytes and historical handle obligations to be resolved; cancellation alone never sets `bytes_removed`.

## Practical next validation gates

First validate owner generations locally: competing owners, killed PostgreSQL ownership connection, blocked input/fsync, stale recordCopy, new-owner cancellation rejection, old-generation read debt, and lock-order races with rewrite. Then run coordinator and two members as separate subprocesses with independent directories, real PostgreSQL, and ephemeral test CA/server/client certificates. Exercise missing/wrong/expired certificates, unauthorized roles, copied-root identity attempts, malformed/truncated fixed/chunked bodies, missing terminal records, final checksum failure, lost write/read/cancel replies, coordinator and member crashes, half-open connections, slow consumers, range bounds, capacity exhaustion, and shutdown while writes/reads run.

Do not infer whole-AZ durability from subprocesses, metadata HA from a single PostgreSQL fixture, or safe volume takeover from a session lock. Until trusted old-process/volume fencing exists, unsupported identity takeover and unresolved old-generation operations are deliberate availability/cleanup limits. This limitation still permits useful authenticated process transport without weakening accepted-mail or erasure claims.
