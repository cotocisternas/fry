# Portable storage and IMAP: focused feasibility notes

Investigated 2026-10-17 against primary source code and official documentation. This follows [discovery](../design/discovery.md) and the requirement to support both self-hosted and managed cloud deployments. No technologies are selected here. Scope is interface and failure semantics, not a benchmark, complete architecture, or vendor comparison.

Reported workload is tens of millions of messages/day, with batches around 500,000 and unknown arrival duration. Typical complete messages are reportedly below 1 MB, but the average and maximum are unknown. Original retention is independent of inbox deletion, lasts days to months, and varies by organization. Backlogged processing is acceptable. These facts do not yet determine peak throughput, storage capacity, or a sufficient database topology.

Current scope after subsequent decisions: first production is AWS São Paulo, one region across multiple AZs, targeting no accepted-mail loss and restored receipt/access within five minutes after one AZ fails. Whole-datacenter or whole-region recovery remains a requirement for later resilient multi-site profiles. The regional-loss analysis below applies to those profiles, not the initial single-region installation. These are required failure tolerances, not demonstrated capabilities.

Existing IMAP integrations use folders, moving messages, or server-side searches. Required searches cover email headers, dates, and flags such as read/unread; body text and attachment-content search are not business requirements. Subsequent decisions establish a conventional shared mailbox as the first-milestone default. Independent application views, with separate folders, flags, and deletions, are optional later features; their delivery completes on availability without waiting for an application action. Exact folder operations/layout still need clarification. Compatibility evaluation must account for actual client usage and protocol conformance, and later for metadata growth with application/view count.

## Gluon: what the source demonstrates

Inspection uses commit `2561acfbad82c2ef0f576a8df98b3269a0cbbfee` dated 2026-10-09.

- **Storage is replaceable, but not through a connection-string swap.** The default builder uses SQLite and an on-disk store. `WithDBClient` accepts a custom implementation of `db.ClientInterface`; it must create clients with read/write transactions implementing Gluon's mailbox, message, subscription, and connector operations. The inspected default implementation opens SQLite databases per user. [Builder](https://github.com/ProtonMail/gluon/blob/2561acfbad82c2ef0f576a8df98b3269a0cbbfee/builder.go), [options](https://github.com/ProtonMail/gluon/blob/2561acfbad82c2ef0f576a8df98b3269a0cbbfee/option.go), [DB contract](https://github.com/ProtonMail/gluon/blob/2561acfbad82c2ef0f576a8df98b3269a0cbbfee/db/client.go), [transaction operations](https://github.com/ProtonMail/gluon/blob/2561acfbad82c2ef0f576a8df98b3269a0cbbfee/db/ops.go), [SQLite implementation](https://github.com/ProtonMail/gluon/blob/2561acfbad82c2ef0f576a8df98b3269a0cbbfee/internal/db_impl/sqlite3/client.go).
- **Active state is local to a process.** The backend holds registered users in a map protected by a Go mutex. Each user holds active states in another map, local synchronization primitives, and an update-processing goroutine. **Inference:** putting storage in a shared service does not by itself prove that two Gluon processes serving the same mailbox maintain consistent UIDs, sequence views, notifications, and deletion safety. No cluster coordination guarantee was established in this investigation. [Backend](https://github.com/ProtonMail/gluon/blob/2561acfbad82c2ef0f576a8df98b3269a0cbbfee/internal/backend/backend.go), [user state](https://github.com/ProtonMail/gluon/blob/2561acfbad82c2ef0f576a8df98b3269a0cbbfee/internal/backend/user.go).
- **Its store has a deletion lifecycle.** Startup processing removes messages marked deleted, then reconciles the store against database IDs. Reconciliation calls `Store.List`, obtains all DB message IDs, and deletes store IDs missing from the DB. Deletion processing also invokes `Store.Delete`. **Inference:** using the retained-original namespace directly as this store would require careful adaptation; treating Gluon deletion as permission to destroy retained originals violates FRY's agreed lifetime separation. The full-store enumeration also needs a large-mailbox startup benchmark. [Deletion and reconciliation code](https://github.com/ProtonMail/gluon/blob/2561acfbad82c2ef0f576a8df98b3269a0cbbfee/internal/backend/user.go).

**Candidate seam:** an independently retained original plus inbox membership/IMAP state, with Gluon's store acting as a view or cache whose removal cannot erase the retained original. This is a proposal, not a demonstrated integration. A single active owner per user/mailbox shard is another hypothesis worth testing; fencing, takeover, reconnect behavior, hot-shard limits, and UID continuity would still need design and failure tests.

As a comparison, `emersion/go-imap/v2` exposes a session interface implementing operations such as `Select`, `Fetch`, `Store`, `Expunge`, `Poll`, and `Idle`. That gives FRY control over its backend but leaves significant mailbox and concurrent-session behavior to the implementation. The README still describes v2 as in development. It is an alternative spike, not evidence that writing a correct clustered backend is simpler. [Session interface](https://github.com/emersion/go-imap/blob/master/imapserver/session.go), [README](https://github.com/emersion/go-imap).

## Portable blob contract: useful S3 facts, not a vendor equivalence claim

Amazon S3 documents strong read-after-write consistency for object PUT/DELETE and subsequent GET/LIST, with atomic updates to a single key. It does not provide atomic updates across multiple keys. Those guarantees apply to Amazon S3; another service advertising an S3-compatible API needs separate verification. [Amazon S3 consistency](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).

Amazon S3 supports `If-None-Match: *` to prevent overwriting an existing key. Concurrent attempts can produce `412 Precondition Failed`; concurrent deletion can produce `409 Conflict`, with different retry behavior for PUT versus multipart completion. Versioned buckets evaluate the current version, and a current delete marker allows creation. **Proposal:** stable ingest identifiers and create-only writes can make one upload attempt retryable. An existing object must be checked against the expected identity/content before treating conflict as success. This does not deduplicate distinct SMTP deliveries automatically. [Conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

Amazon S3 lifecycle expiration is asynchronous. In versioned buckets, ordinary expiration can create a delete marker while old versions remain. **Implication:** define logical unavailability at retention expiry separately from physical erasure, and test version cleanup explicitly. [Lifecycle expiration](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html).

**Portable contract to validate:** write/read/delete semantics, conditional-write support, integrity checking, acknowledged-write durability, listing behavior, incomplete-upload cleanup, expiration, and behavior during failures. FRY can require this contract without requiring every cloud and self-hosted installation to use the same product.

## Metadata and durable work: candidate protocol

PostgreSQL transactions make a group of database changes atomic. That supports committing a message record and pending-work/outbox record together. This is an application pattern inferred from transaction guarantees, not a built-in transaction spanning PostgreSQL and object storage. [Transactions](https://www.postgresql.org/docs/18/tutorial-transactions.html).

**Proposal to test:** persist the original first, then commit message ownership/envelope metadata and pending work in one database transaction; only acknowledge SMTP success after the chosen durability requirements are satisfied. A failed metadata transaction leaves an object requiring reconciliation. A committed transaction followed by a lost SMTP reply can lead to another delivery. Cleanup must never race a live ingest attempt. IMAP-source checkpointing and deletion must similarly wait until the accepted ingest state is recoverable. Other designs, such as accepting into a durable log before blob materialization, remain possible and were not evaluated here.

`SELECT ... FOR UPDATE SKIP LOCKED` is explicitly documented for multiple consumers of queue-like tables, while offering an inconsistent view unsuitable for general queries. **Proposal:** claim work in short transactions with leases; perform scanning/network calls outside database locks. Recover expired claims and make completion retry-safe. An outbox publisher can publish twice if it crashes after sending but before recording completion, so consumers still need idempotency. No broker choice or exactly-once guarantee follows. [Row locking](https://www.postgresql.org/docs/18/sql-select.html#SQL-FOR-UPDATE-SHARE).

PostgreSQL streaming replication is asynchronous by default; acknowledged primary commits can be missing on a promoted standby. **Implication:** FRY's durability contract must specify replication/commit behavior and recovery objectives, not merely that PostgreSQL is present. Self-hosted and managed deployments need equivalent acceptance guarantees even if their operational mechanisms differ. [Replication](https://www.postgresql.org/docs/18/warm-standby.html#SYNCHRONOUS-REPLICATION).

### Consequence of the accepted-mail regional-loss requirement

Amazon S3 explicitly describes Cross-Region Replication as asynchronous. **Inference:** accepting mail after a single-region PUT and merely enabling CRR does not establish zero accepted-mail loss if that region fails before copying completes. Even a bounded replication-delay objective is different from durable remote receipt before SMTP acceptance. [S3 replication](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication.html).

PostgreSQL synchronous replication can require a commit to wait for confirmation that selected standby servers have persisted it. Its guarantees depend on configuration and standby placement. This still does not replicate the message blob or implement the complete failover system. **Open topology requirement:** before final acceptance, message bytes and sufficient recovery/ownership/work state must survive the agreed site failure; enforce this across every durable component. Candidate mechanisms include independently confirmed writes or an appropriately replicated durable ingest log, but neither has been selected or tested. Safe promotion/fencing, cross-site latency, and behavior when a site or inter-site link is unavailable remain design work. [Synchronous replication](https://www.postgresql.org/docs/18/warm-standby.html#SYNCHRONOUS-REPLICATION).

## Expiration and scale constraints

PostgreSQL documents that detaching/dropping partitions can remove large amounts of data much faster than bulk DELETE and avoid its vacuum overhead. Partitioned-table unique/primary-key constraints must include every partition-key column. **Implications:** time partitioning affects message identity and cross-time deduplication; per-organization retention complicates whole-partition expiry; deleting metadata before retaining a durable blob-deletion manifest can lose cleanup information. Partitioning does not itself distribute writes across database servers. [Partitioning](https://www.postgresql.org/docs/18/ddl-partitioning.html).

For scale intuition only, 10 million arrivals/day retained for 30 days means 300 million original-message records before memberships, documents, processing attempts, or audit records. This arithmetic is not the agreed design target. Neither PostgreSQL throughput nor a particular object-store configuration has been demonstrated sufficient.

## Minimum evidence before selecting the foundation

1. Measure burst duration, concurrent batches, byte distribution, and concentration per organization/inbox. Define accepted-message durability, maximum processing delay, and overload behavior.
2. Spike IMAP reconnect, simultaneous clients, deletion versus retained recovery, UID stability, ownership takeover, and large-mailbox startup. Compare Gluon adaptation cost with a custom session backend only against required client behaviors.
3. Run one ingest failure matrix against both proposed deployment profiles: failures before/after blob write, DB commit, SMTP reply, work claim, webhook completion, and retention cleanup. Include ambiguous timeouts and failover.
4. Benchmark the whole write/read lifecycle at retained data scale: metadata indexes, WAL/replication, work-queue churn, spam scanning, IMAP fetch/search, blob request costs, and expiry. Test hot tenants as well as aggregate traffic; determine whether sharding is needed from evidence.

No implementation, provisioning, throughput test, or self-hosted S3 vendor verification was performed.
