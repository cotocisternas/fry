# Local Kubernetes rehearsal profile

Checked 2026-10-17. This prepares a later disposable **local** rehearsal after the [container smoke](container-deployment.md). No cluster creation, image load, manifest application or AWS action was performed. The [EKS research](eks-deployment-feasibility.md) remains the separate deployment constraint: this exercise cannot establish AZ independence, accepted-mail recovery within five minutes, or production capacity.

## Verified versions and bounded scope

Installed tools report kind **v0.33.0**, Linux amd64, and kubectl **v1.37.1**. The official kind release defaults to Kubernetes **v1.37.0** and publishes:

`kindest/node:v1.37.0@sha256:a1ed56cfb0e7b93589bdf97c8cd566405a265939e3620fc4f5de89adff580ae5`

Metadata-only `docker buildx imagetools inspect` confirmed that exact index exists; its amd64 manifest is `sha256:1aac8018c42eb5d48fae5be507caaee789fc6d9b9b3f560359dd4157ac00d4f6`. The index also supports arm64; choose the host architecture. These are upstream release images, not a custom node build. [kind v0.33.0 release](https://github.com/kubernetes-sigs/kind/releases/tag/v0.33.0).

Use one control-plane node, the default networking/storage components, one fresh namespace, one synthetic PostgreSQL instance, two distinct remote members with separate PVCs and IDs, and one coordinator. No Ingress, LoadBalancer controller, NodePort, host networking, real certificate issuance, outbound internet mail or production credentials. More kind nodes would still share this machine's resources and failure boundary. Set the API bind explicitly to `127.0.0.1`, choose its port automatically, and omit extra host mounts/port mappings. [kind configuration](https://kind.sigs.k8s.io/docs/user/configuration/).

Suggested initial **test budgets**, not upstream minima or measured requirements: reserve four host CPUs, 8 GiB available RAM and 15 GiB free runtime-disk space; bound the workload to 32 messages of 64 KiB. Start FRY containers at requests 100m/128Mi and limits 1 CPU/512Mi; PostgreSQL at 250m/256Mi and limits 1 CPU/1Gi. Allow control-plane overhead outside those pod budgets. Record actual usage and OOM/restart counts before increasing work. Requests affect scheduling and limits affect execution; memory limits can terminate a container rather than fail a write cleanly. [Kubernetes resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/).

The read-only host check found 62 GiB RAM (39 GiB available) and 657 GiB free on the repository filesystem; this does not verify available space in the selected container runtime's storage root. Check that root separately. Nonroot FRY processes are independent of whether kind's node provider runs rootless. Switching the provider to rootless adds cgroup-v2/delegation and runtime requirements; do not change host settings as part of this rehearsal. [kind rootless requirements](https://kind.sigs.k8s.io/docs/user/rootless/).

## Image and kubeconfig isolation

Build the repository's actual [Dockerfile](../../Dockerfile) for the host Linux architecture using a unique run tag; require the preceding [container smoke (`smoke.sh containers`)](../../scripts/smoke.sh) to pass for that image. With buildx, `--load` makes the single-platform result available in the local Docker image store. Then use `kind load docker-image <unique-tag> --name <unique-cluster>`; every FRY pod must use that same tag and explicit `imagePullPolicy: Never`. Preload the digest-pinned PostgreSQL image too, rather than rely on a mutable public tag or accidentally pull a different application image. kind documents both image loading and pull-policy requirements. [kind image workflow](https://kind.sigs.k8s.io/docs/user/quick-start/#loading-an-image-into-your-cluster), [Docker buildx load](https://docs.docker.com/reference/cli/docker/buildx/build/#load).

The eventual runner must create a private temporary directory (`umask 077`), a unique cluster name, and an initially absent absolute kubeconfig path inside it. Pass `--kubeconfig "$rehearsal_kubeconfig"` to **kind create**; do not merge with or modify the user's default kubeconfig. kind's explicit flag selects only that file. Every kubectl invocation must carry that exact `--kubeconfig`, `--context "kind-$rehearsal_cluster"`, and explicit namespace where applicable. Before writes, verify the generated config has exactly the expected context and an HTTPS API endpoint on numeric `127.0.0.1`; reject reused directories/files or unexpected endpoints. Do not run `use-context`, accept a kubeconfig argument from the ambient environment, or fall back to the current context. [kind kubeconfig behavior](https://kind.sigs.k8s.io/docs/user/quick-start/#interacting-with-your-cluster).

Capture the generated cluster name and delete **only that name**, including failure cleanup. Use bounded readiness waits and subprocess deadlines, retain redacted diagnostics on failure, and stop background port-forward processes before deletion. Kind deletion is destructive to this disposable cluster's local storage; it is not a backup test.

## PVC and process security

kind v0.33.0 embeds `standard`, backed by `rancher.io/local-path`, with `WaitForFirstConsumer` and reclaim policy `Delete`. Its helper creates writable directories under `/var/local-path-provisioner` inside the node and removes them on teardown. Use `storageClassName: standard` explicitly and let scheduling bind the claims; a Pending PVC before its consuming pod is scheduled is expected. Do not set `nodeName` to bypass scheduling. [Versioned kind storage manifest](https://github.com/kubernetes-sigs/kind/blob/v0.33.0/pkg/build/nodeimage/const_storage.go), [binding semantics](https://kubernetes.io/docs/concepts/storage/storage-classes/#volume-binding-mode).

Request one 1Gi RWO PVC per member and a separate synthetic database claim. These requests do **not** enforce capacity with local-path; set each member's FRY capacity to a small explicit bound (for example 128 MiB), retain an aggregate input bound and monitor runtime disk space. All three claims share host disk. RWO also allows multiple pods on one node; it is not a single-process ownership fence. Keep each member at one pod and never mount its claim into another live member. [Local-path limitations](https://github.com/rancher/local-path-provisioner#cons), [PV access modes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes).

For FRY use UID/GID 65532, `runAsNonRoot: true`, `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false`, capabilities drop `ALL`, seccomp `RuntimeDefault`, and `automountServiceAccountToken: false`. Mount configs/TLS secrets read-only and readable by that UID/group. Add bounded writable `/tmp` only if needed. Disable packing initially so no scratch/object-store dependency is introduced. Configure member data as a private child of its mounted claim: kind's helper creates the mount root mode 0777, so UID 65532 can create its own mode-0700 child without a root init container. Verify this behavior in the rehearsal; do not assume `fsGroup` changes every backend. `fsGroup: 65532` and `fsGroupChangePolicy: OnRootMismatch` are useful where ownership management is supported, but are not permission proof. [Security contexts](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/).

The PostgreSQL image has its own UID and writable-directory requirements; do not copy FRY's numeric UID or read-only-root settings blindly. Pin and inspect the image already used by the container smoke, use fresh fixture credentials/schema, and validate its data/socket/temp mounts independently. No database or member data may be placed in a ConfigMap or the container image layer.

## Services, TLS and shutdown

Use internal ClusterIP TCP Services for database, each member, and coordinator protocol ports. Certificates issued by the fixture CA must cover Service DNS names used for member connections; keep coordinator key pins/mTLS enabled. Client-facing FRY listeners must bind a numeric nonloopback pod address with the existing explicit TLS/STARTTLS mode; loopback development plaintext cannot receive Service traffic. Expose only the tested SMTP/IMAP endpoints to the host with `kubectl ... port-forward --address 127.0.0.1`, never `0.0.0.0`. Preserve TLS hostname verification through the tunnel using the fixture's expected server name. A port-forward tests a selected pod stream, not cloud load balancing or the complete Service network path. Also perform a bounded in-cluster protocol check against the Service DNS name. [kubectl port-forward](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_port-forward/).

Use TCP startup/readiness probes as listener checks, plus end-to-end authenticated acceptance and exact IMAP fetch assertions. They do not establish database/replica health. Omit aggressive liveness probes in this slice. Set `terminationGracePeriodSeconds: 60` explicitly (never below 20 here); it must cover the member's existing 15-second close budget plus overhead. Stop coordinator traffic/process first, await closure, then members, then database. Measure actual completion rather than assume the grace value proves drain. Avoid shell preStop hooks in the distroless image. [Probe semantics](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/).

For the first controlled rehearsal, plain member Pods with explicit `restartPolicy: Never` make failures observable without automatic retry; recreate only after clean closure is verified. Deployments permit only `Always`, and the Pod default is also `Always`. Neither automatic retries nor a StatefulSet can clear FRY's unclosed-owner fence. An OOM, SIGKILL or forced pod deletion may therefore produce intentional startup refusal, not successful recovery; preserve diagnostics and never reset ownership/PVCs to make that test appear green. Normal termination sends SIGTERM and later SIGKILL if the grace expires. [Pod lifecycle and restart policy](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/), [FRY owner authority](../../internal/receiptstore/member_owner_linux.go).

Acceptance evidence should record image IDs, node version, PVC bindings, security settings, zero unexpected restarts, SMTP receipt/IMAP exact content, rejection of an unauthenticated member client, bounded termination, and successful clean same-PVC member reopen. Finish by deleting only the generated cluster and temporary secrets. Passing proves this local configuration works on one host; persistence across cluster deletion, cloud storage, scheduler/node failures, real ingress, rolling upgrade and AZ recovery remain untested.
