# IMAP compatibility extensions and APPEND framing

Investigated 2026-10-17 against the pinned `github.com/emersion/go-imap/v2 v2.0.0-beta.8`, commit `7ac47a9cfd9a06ff5f3bdee52d7420137f023a1e`, and `go-message v0.18.2`. Sources are available under `/home/coto/go/pkg/mod/github.com/emersion/go-imap/v2@v2.0.0-beta.8` and `/home/coto/go/pkg/mod/github.com/emersion/go-message@v0.18.2`. This extends [the adapter investigation](imap-adapter-implementation.md). Current FRY raw/HEADER/TEXT reads already stream retained bytes; ENVELOPE, MIME sections, BODYSTRUCTURE, and APPEND require additional behavior. Recommendations below are implementation proposals, not measured production guarantees.

## APPEND: confirmed upstream framing defects

A fresh loopback TCP server using unmodified beta.8 and an `Append` backend calling `io.ReadAll` produced these results after LOGIN and `b APPEND INBOX {5}\r\n`:

| Bytes sent after continuation | Backend observes | Client observes |
| --- | --- | --- |
| `abc`, then TCP `CloseWrite()` | `Size()==5`, three bytes, nil error | EOF without tagged reply |
| `abcde invalid-tail\r\n` | Five bytes, nil error | No tagged reply before a short test read deadline |
| `abcde\r\n` | Five bytes, nil error | `b OK [APPENDUID 1 1] APPEND completed` |

The temporary reproducer is `/tmp/fry-imap-extension-repro/main.go`; it did not use FRY persistence. It establishes that a backend treating full-reader success as permission to commit can accept a truncated literal or malformed command. It does not claim the current FRY backend already commits such commands.

`LiteralReader` wraps a limited reader and passes premature source EOF through unchanged. More fundamentally, `handleAppend` invokes `Session.Append` **before** checking the optional UTF8 closing parenthesis and trailing CRLF. It then returns an earlier nil `err` on drain failure and on CRLF parse failure. Correcting those returned errors alone does not undo a backend commit. [Literal decoder](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/internal/imapwire/decoder.go), [APPEND handler](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/imapserver/append.go).

### Recommended minimal streaming patch

Keep the pinned upstream copy and its MIT notice isolated, recording the exact patch and regression tests. Wrap the parsed literal inside the APPEND handler, preserving `imap.LiteralReader` (`io.Reader` plus `Size() int64`). The wrapper should:

1. Track the exact declared byte count and a sticky terminal result. Convert source EOF before that count to `io.ErrUnexpectedEOF`; never fabricate missing bytes.
2. When a read obtains the final payload chunk, **withhold that chunk from the backend until framing is validated**. Complete the underlying literal's EOF transition so the decoder leaves literal mode; then check the optional UTF8 `)` and exact command CRLF.
3. On valid framing, expose the withheld bytes and then clean EOF. On invalid framing, return **zero bytes and the framing error for that final read**, even though its buffer was filled internally. Returning `n > 0, err` is insufficient: `io.CopyN` can report success once it has copied the requested byte count, discarding the accompanying error. Earlier chunks may already be staged, but the backend cannot have received the complete literal.
4. For a zero-length literal, validate framing **before invoking the backend**. A backend using `io.CopyN(..., 0)` never calls Read.
5. Make repeated reads return the cached EOF/error without parsing another command. Route handler draining through the same wrapper and remove duplicate trailer parsing. Propagate the actual drain/decoder errors instead of the old `err` variable.

This moves proof of complete command framing ahead of a correctly implemented backend observing all declared bytes, without a whole-message buffer or disk spool. Backend errors must abort staged receipt state; success remains conditional on durable receipt plus mailbox state. The wrapper cannot make a backend that intentionally commits unread/truncated input correct. This algorithm is a proposed patch, **not an executed patch result in this research**. [Go CopyN implementation](https://go.dev/src/io/io.go), [existing handler](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/imapserver/append.go).

An alternative is a two-phase backend hook that stages bytes, then commits only after the handler validates framing, with explicit abort on every failed path. A disk spool before invoking the existing backend also works but adds another capacity and cleanup budget. The final-chunk wrapper is the smallest seam for FRY's existing streaming acceptance path.

### Backend boundary and test gates

`Session.Append(mailbox string, r imap.LiteralReader, options *imap.AppendOptions) (*imap.AppendData, error)` receives optional flags and internal date. Return destination UID/UIDVALIDITY only after durable membership creation. `SessionAppendLimit.AppendLimit() uint32` overrides the library's 100 MiB default; match it to configured receipt limits. Do not interpret APPEND as outgoing SMTP submission. [Session API](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/imapserver/session.go), [APPEND types](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/append.go), [APPEND semantics](https://www.rfc-editor.org/rfc/rfc9051.html#section-6.3.12).

Add actual TCP regressions for short/empty/complete literals, malformed or missing CRLF, invalid/missing UTF8 `)`, synchronous and allowed nonsynchronizing literals, data arriving one byte at a time, pipelined next commands, early backend failure and bounded drain, and a backend using both ReadAll and CopyN. Assert that malformed inputs create no visible receipt/membership, never return tagged OK, and cannot poison the next valid command. Test zero-size handling separately, including empty data followed by invalid tail. Then exercise 200 MiB streaming, retained exact bytes, initial flags/date, read-only selected-state versus explicit destination rules, quota/capacity failures, cancellation, durable-commit failure, and lost final replies. Lost successful replies can still cause a client to repeat APPEND; do not claim exactly-once external retry behavior.

## Header-field FETCH and ENVELOPE

`FetchItemBodySection` already carries `HeaderFields`, `HeaderFieldsNot`, `Specifier`, `Part`, `Partial`, and `Peek`. For HEADER.FIELDS/NOT, select complete original header fields with their folded continuation lines and duplicates; compare names case-insensitively. Preserve order and bytes, append the required header/body separator, then apply the requested partial range to the filtered result. MIME or message header selection belongs to the selected part, not always the top-level message. Header selection need not read attachment bodies. [FETCH types](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/fetch.go), [rev1 section and partial semantics](https://www.rfc-editor.org/rfc/rfc3501.html#section-6.4.5).

The bounded first step is top-level header filtering plus ENVELOPE over the already bounded header block. `imapserver.ExtractEnvelope(textproto.Header) *imap.Envelope` returns structured metadata, and `FetchResponseWriter.WriteEnvelope(*imap.Envelope)` writes it. The helper is not fully lossless validation: it ignores several parser errors and has a TODO for address groups. Its writer supplies Sender and Reply-To from From when nil. Test quoted names, encoded words, groups including empty groups, repeated fields, missing/invalid date, and missing Sender/Reply-To before claiming broad compatibility. Use a separate parsed representation for metadata; never reserialize it into raw BODY[] output. [Envelope helper](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/imapserver/message.go#L210), [envelope writer](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/imapserver/fetch.go#L509).

`go-message/textproto.ReadHeader(*bufio.Reader) (Header,error)` explicitly requires a bounded source for denial-of-service protection. A bufio size alone is not a header limit: continued lines can grow. Its representation preserves raw fields, but parsing budgets still belong to FRY. Character decoding should be explicit; the package documents registering its charset support separately. [Header parser](https://github.com/emersion/go-message/blob/v0.18.2/textproto/header.go), [charset registration](https://github.com/emersion/go-message/blob/v0.18.2/message.go).

## BODYSTRUCTURE and MIME sections without whole-message buffers

Exact output APIs are `FetchResponseWriter.WriteBodyStructure(imap.BodyStructure)` and `WriteBodySection(*imap.FetchItemBodySection, int64) io.WriteCloser`. Construct `*imap.BodyStructureSinglePart` or `*imap.BodyStructureMultiPart`; single parts carry content type/parameters, ID, description, transfer encoding, encoded-body byte size, optional Text line count, and optional MessageRFC822 envelope/child structure/line count. Extended output also needs disposition, language, location, and multipart parameters. Every extended node must have nonnil `Extended`; the writer dereferences it. Multipart with zero children panics. Validate the complete tree before emitting a response. [Body structure types](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/fetch.go), [body structure writer](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/imapserver/fetch.go#L609).

Avoid `ExtractBodyStructure`, `ExtractBodySection`, and `ExtractBinarySection` for 200 MiB mail: they allocate body/section buffers, and partial extraction happens after buffering. `go-message`'s high-level Entity readers may decode transfer encoding/charset, which is unsuitable for indexing the original encoded BODY section bytes. Standard multipart parsers can also buffer ahead and hide offsets; counting bytes read from their underlying reader does not identify exact part boundaries. [Extraction source](https://github.com/emersion/go-imap/blob/v2.0.0-beta.8/imapserver/message.go), [entity reader](https://github.com/emersion/go-message/blob/v0.18.2/entity.go), [multipart reader](https://github.com/emersion/go-message/blob/v0.18.2/textproto/multipart.go).

**Proposed module seam:** a bounded scan builds immutable metadata keyed by receipt hash and parser version. Its result maps IMAP part paths to raw header/body spans, parsed envelope/MIME fields, encoded byte counts, and line counts. The scanner reads retained bytes once using fixed buffers and a bounded stack; selected FETCH later streams the known span through `receiptstore.Open`. Header filtering uses bounded raw header spans. For a first prototype, an optional bounded disk snapshot can make multiple passes simpler, with explicit scratch admission and cleanup, but it must not become another permanent copy.

An offset-producing scanner must recognize actual MIME delimiter lines, closing delimiters, preamble/epilogue, nested boundaries, and the CRLF associated with delimiters. Do not infer boundaries from substring matches inside attachments. Keep raw and decoded sizes distinct. Handle `message/rfc822` nested headers/body and IMAP path numbering deliberately. Keep BINARY fetching disabled until decoded-byte ranges and its distinct semantics are implemented. [MIME multipart rules](https://www.rfc-editor.org/rfc/rfc2046.html#section-5.1.1), [IMAP body section interpretation](https://www.rfc-editor.org/rfc/rfc9051.html#section-6.4.5).

Proposed parser budgets: per-header bytes, aggregate header bytes, field count, physical/folded line bytes, MIME depth, part count, boundary length, parameter/address count, metadata bytes, total bytes scanned, elapsed time, and concurrent scans. Specify and test each bound; their numeric values are engineering defaults, not new business requirements. Cap caches and deduplicate simultaneous scans of the same receipt. Treat parse-limit or unsupported malformed structure as a recorded metadata error with an honest failed extended FETCH; retain raw mail and keep raw BODY[] accessible. Optional document filtering must not become mandatory MIME admission.

Before enabling MIME extensions, test large single-part attachments and many small parts; nested multipart and message/rfc822; encoded headers; boundary-like body text; empty/malformed multipart; missing closing delimiter; folded/duplicate part headers; partial ranges at all boundaries; CRLF ownership; transfer-encoded attachments; parser-budget exhaustion; corrupt storage; and concurrent reads while mailbox memberships change. Assert exact bytes against independent fixtures and bounded peak memory, not only output shape. These remaining extensions require protocol and memory tests beyond the APPEND reproductions performed here.
